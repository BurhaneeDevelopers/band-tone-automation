# Burhani Guards Band — Music Transcription Tool
## AI IDE Generation Prompt

---

## PROJECT OVERVIEW

Build a full-stack web application for Burhani Guards marching band to convert any song — including hip hop songs with lyrics from YouTube — into complete band notation with sargam (Sa Re Ga Ma Pa Dha Ni) for all instruments and drum patterns.

**The band's instruments:**
- Trumpet (Bb transposing)
- Alto Saxophone (Eb transposing)
- Trombone (concert pitch)
- Euphonium (concert pitch)
- Drums (snare, hi-hat)
- Bass Drum

**Fixed rule: Sa = C always.** The band always reads in C. Every note in every song must be transposed so that the tonic lands on C before sargam is assigned. This is not relative — C is always Sa, D is always Re, E is always Ga, and so on.

**The core problem being solved:** The band takes songs — including commercially produced hip hop with vocals, fillers, and layered production — and needs to arrange them for their instruments. This currently requires a professional musician spending hours manually identifying notes by ear. This app automates as much of that process as possible, and provides tools to quickly verify and correct the rest.

**Input modes:**
1. YouTube URL — paste a link, the system downloads and processes it
2. Audio file upload — MP3, WAV, and other formats for clean recordings or pre-isolated stems

**Processing approach:** Because commercial songs (especially hip hop) have multiple layers, the pipeline separates audio into stems first (vocals, melody, drums, bass), then transcribes each stem separately, then maps everything to sargam in C with per-instrument transposition applied.

**Hybrid automation:** Full automation is not reliable for all elements — especially barely audible fillers in hip hop production. The app provides a built-in verification player (with slow-down and real-time pitch display) so band members can quickly confirm or manually correct notes that the AI got wrong, without needing a separate application.

Users work in short segments (10–30 seconds) for best accuracy and build up a full arrangement progressively by grouping segments into tone groups.

## ARCHITECTURE

```
Browser
  ↓ YouTube URL  OR  audio file upload
Next.js /api/transcribe-youtube  OR  /api/transcribe-file
  ↓ SSE streaming response (phase events to browser)
Python FastAPI Microservice (Railway)
  │
  ├─ STEP 1: Acquire audio
  │    YouTube URL → yt-dlp → WAV file
  │    File upload → save to temp WAV
  │
  ├─ STEP 2: Source separation (Demucs htdemucs model)
  │    Full mix → 4 stems: vocals, drums, bass, other
  │    Each stem saved as separate WAV
  │
  ├─ STEP 3: Per-stem transcription
  │    vocals + other stems → basic-pitch → melody note events
  │    drums stem → onset/pattern detection → kick/snare/hihat pattern
  │    bass stem → basic-pitch (low freq range) → bass line notes
  │
  ├─ STEP 4: Key detection + transpose to C
  │    Analyse melody note events → detect song's original key
  │    Calculate semitone shift: shift = (0 - tonic_pc) mod 12
  │    Apply shift to all melody + bass notes → everything now in C
  │
  ├─ STEP 5: Sargam mapping (fixed Sa = C)
  │    C=Sa, D=Re, E=Ga, F=Ma, G=Pa, A=Dha, B=Ni (+ komal/tivra variants)
  │
  ├─ STEP 6: Instrument transposition
  │    For each melodic instrument, add that instrument's written offset
  │    Trumpet: +2, Alto Sax: +9, Trombone: 0, Euphonium: 0
  │    Re-apply sargam labels from the instrument's written pitch
  │
  └─ STEP 7: Return structured JSON
       Per-instrument sargam note arrays + drum pattern grid + filler flags

Next.js receives result → stores in Supabase → streams phases to browser
Browser renders per-instrument panels + verification player
```

The Next.js API routes act as SSE proxies — they stream phase events to the browser so the user sees progress through each step. The Python service is stateless. Supabase is written to only after successful transcription when the user explicitly saves.

## PYTHON TRANSCRIPTION SERVICE

### Location: `/services/transcription`

### Overview
Stateless FastAPI service. Receives either a YouTube URL or an audio file. Runs the full 7-step pipeline and returns a structured JSON result. Streams progress events via SSE so the frontend shows which step is running. Requires minimum 4GB RAM on Railway due to Demucs model size (~830MB).

---

### STEP 1 — Audio Acquisition

**If YouTube URL:**
- Use `yt-dlp` to download best available audio stream
- Convert to WAV 44100Hz mono using ffmpeg subprocess
- Enforce max duration: 300 seconds (5 minutes). Reject longer with clear error.
- Store in temp directory with unique session ID

**If file upload:**
- Accept mp3, wav, ogg, flac, m4a, aac — max 50MB
- Convert to WAV 44100Hz mono using ffmpeg for consistent downstream processing
- Store in temp directory

**yt-dlp options to set:**
- `--extract-audio --audio-format wav`
- `--no-playlist` (never download full playlists)
- `--max-filesize 100m`
- User-agent spoofing to avoid bot blocking
- If yt-dlp fails (geo-block, private video, age-gate), return a specific 422 error with the reason so the frontend can display a helpful message

---

### STEP 2 — Source Separation (Demucs)

Use Meta's `demucs` library with the `htdemucs` model (4 stems).

**Output stems:**
- `vocals.wav` — lead and background vocals
- `drums.wav` — all drum and percussion elements
- `bass.wav` — bass guitar, 808 bass, sub bass
- `other.wav` — everything else: synths, guitars, piano, melodic fillers, pads

**Which stems carry the melody for band arrangement:**
- Primary melody: `other.wav` — this is what trumpet, sax, trombone, euphonium will play
- Secondary melody check: `vocals.wav` — if `other` is sparse, the vocal line is the melody
- Filler detection: run basic-pitch on both `other` and `vocals`, merge note events, flag notes that appear in one but not the other as "filler candidates" so the human can review them in the verification player
- Rhythm: `drums.wav` → drums instrument
- Low melody/bass line: `bass.wav` → can optionally feed euphonium or trombone the bass notes

**Demucs performance note:** On Railway with CPU only, separation takes 2–4x real-time (a 30-second clip = 60–120s processing). Make this clear in the SSE phase events.

---

### STEP 3 — Per-Stem Transcription

**Melody stems (other + vocals):**
Run `basic-pitch` on each stem separately with these settings:
- `onset_threshold`: 0.5
- `frame_threshold`: 0.3
- `minimum_note_length`: 80ms (shorter = captures fast hip hop fillers better)
- `minimum_frequency`: 80Hz
- `maximum_frequency`: 1800Hz

Merge note events from both stems. Where note events overlap in time (within 50ms), keep the one with higher velocity/confidence. Flag notes that only appear in one stem as `source: "filler"` vs `source: "melody"` — this flag is passed to the frontend so filler notes can be visually distinguished.

**Drums stem:**
Use `librosa.onset.onset_detect` on the drums WAV. Then classify each onset as kick, snare, or hi-hat using frequency analysis:
- Kick (bass drum): dominant energy below 150Hz
- Snare: dominant energy 150–500Hz with transient
- Hi-hat: dominant energy above 5000Hz

Map onsets to a beat grid (16th-note resolution, auto-detected BPM using `librosa.beat.beat_track`). Output as a pattern grid: `[[beat_position, type, velocity], ...]`

Bass drum and snare drum are output as separate patterns for the separate band instruments.

---

### STEP 4 — Key Detection and Transpose to C

**Sa = C is fixed for this band. All output must be in C.**

Detect the original key of the song from the merged melody note events:
- Build pitch class histogram weighted by note duration × velocity
- Correlate against Krumhansl-Kessler major key profile for all 12 keys
- Take the highest-scoring key as the original tonic
- Also test minor key profile — if minor scores higher, record it but still transpose to C major (the band reads major)

**Transposition:**
- `shift_semitones = (0 - tonic_pitch_class) % 12`
- Apply shift to every MIDI note number in melody and bass note events
- All notes now land in C major (C=0, D=2, E=4, F=5, G=7, A=9, B=11)
- Store `original_key` (e.g. "F#") in the response for reference

Drum patterns do not need transposition — they are rhythmic, not pitched.

---

### STEP 5 — Sargam Mapping (Fixed Sa = C)

After transposing to C, mapping is deterministic — no key parameter needed:

```
C  = Sa
C# = re  (komal Re)
D  = Re
D# = ga  (komal Ga)
E  = Ga
F  = Ma
F# = Ma+ (tivra Ma)
G  = Pa
G# = dha (komal Dha)
A  = Dha
A# = ni  (komal Ni)
B  = Ni
```

Octave markers: `'` per octave above C4, `,` per octave below C4. Middle octave (C4–B4) has no marker.

Each note object in the output includes: `sargam`, `note` (western letter), `midi`, `start`, `end`, `duration`, `velocity`, `source` ("melody" | "filler"), `confidence` (0–1 from basic-pitch).

---

### STEP 6 — Instrument Transposition

The melody is now in C. Each transposing instrument reads in a different written key, so apply the written offset to each instrument's copy of the notes:

- **Trumpet (Bb):** written pitch = concert pitch + 2 semitones. Written key = D. Player reads D=Sa, E=Re, F#=Ga...
- **Alto Saxophone (Eb):** written pitch = concert pitch + 9 semitones. Written key = A. Player reads A=Sa, B=Re, C#=Ga...
- **Trombone:** concert pitch, no shift. Reads C=Sa, D=Re...
- **Euphonium:** concert pitch, no shift. Reads C=Sa, D=Re...
- **Drums:** no pitch. Pattern grid only.
- **Bass Drum:** no pitch. Pattern grid only (kick onsets from drums stem).

For each instrument, after applying the written offset, re-map to sargam using the same fixed C-based table above but shifted. This means the sargam syllables remain the same (Sa Re Ga Ma...) but the western note letters differ per instrument — which is correct and expected.

---

### STEP 7 — Response JSON Shape

```
{
  original_key: string,            // e.g. "F#" — key before transposing to C
  transposed_to: "C",              // always C
  detected_bpm: number,
  duration: number,
  note_count: number,
  separation_quality: string,      // "good" | "fair" | "poor" — heuristic from Demucs confidence
  instruments: {
    trumpet: {
      label: "Trumpet (Bb)",
      written_key: "D",
      transposition: 2,
      notes: [
        {
          start: number,           // seconds
          end: number,
          duration: number,
          sargam: string,          // e.g. "Re'", "Ma", "ga,"
          note: string,            // western written note e.g. "E"
          midi: number,
          velocity: number,
          source: "melody"|"filler",
          confidence: number       // 0–1
        }
      ]
    },
    alto_saxophone: { ... },       // written_key: "A", transposition: 9
    trombone: { ... },             // written_key: "C", transposition: 0
    euphonium: { ... },            // written_key: "C", transposition: 0
    drums: {
      label: "Drums",
      bpm: number,
      pattern: [
        { beat: number, subdivision: number, type: "snare"|"hihat"|"hihat_open", velocity: number }
      ]
    },
    bass_drum: {
      label: "Bass Drum",
      bpm: number,
      pattern: [
        { beat: number, subdivision: number, velocity: number }
      ]
    }
  }
}
```

- `yt_geo_blocked` — video not available in server region
- `yt_private` — private video
- `yt_too_long` — video exceeds 5-minute limit
- `no_notes` — no pitched notes detected after separation
- `separation_failed` — Demucs model error
- `file_too_large` — exceeds 50MB
- `unsupported_format` — file type not accepted

## VERIFICATION PLAYER PAGE — DETAILED FEATURE LOGIC

This is the hybrid manual correction interface. Its job is to let a band member quickly confirm or fix any note the AI got wrong, especially fillers.

### Layout
Split screen:
- Left (60%): Audio player + note timeline
- Right (40%): Active note editor + instrument tabs

### Audio Player (Wavesurfer.js)
- Waveform display of the original audio (not a stem — the full mix so the user can hear everything)
- Playback speed control: 1x, 0.75x, 0.5x, 0.25x
- Loop toggle: loops a selected time region
- Real-time pitch display: as audio plays, show which sargam note is currently being detected from the audio using a simple real-time FFT (client-side, using Web Audio API). Display it as a large label "Currently hearing: Pa" — updates 10 times per second. This helps the user confirm whether the AI note matches what they hear.
- Playhead position shows current time in seconds
- Clicking the waveform seeks to that position

### Note Timeline
- Horizontal scrollable timeline below the waveform
- One row per instrument (6 rows: trumpet, alto sax, trombone, euphonium, drums, bass drum)
- Each note shown as a colored block spanning its start–end time
- Filler notes shown in a different color (orange/amber)
- Low-confidence notes have a dashed border
- Clicking a note block: selects it, seeks audio to that note's start time, opens the note editor on the right
- Timeline is synchronized with the audio playhead

### Note Editor (right panel)
When a note is selected:
- Shows: current sargam, western note, start time, duration, confidence, source stem
- **Sargam correction:** a 12-button grid showing all sargam options (Sa, re, Re, ga, Ga, Ma, Ma+, Pa, dha, Dha, ni, Ni) — user clicks to reassign the note
- Octave up/down buttons
- "Delete note" button — removes the note from this instrument's array
- "Add note before/after" — opens an insert mode where clicking the timeline adds a new note at that position (user picks sargam from the grid)
- Keyboard shortcuts: left/right arrows = previous/next note, space = play/pause, 1–9 = sargam shortcuts

### Filler Review Mode
- A dedicated "Review Fillers" button activates a guided mode
- Jumps to each filler note in sequence, plays 2 seconds before it, pauses
- User hears it and clicks: "Keep" | "Fix" | "Delete"
- "Keep" = mark as confirmed, remove filler flag
- "Fix" = open sargam grid to correct it
- "Delete" = remove from all instrument arrays
- Progress bar: "Reviewing filler 3 of 11"

### Drum Pattern Editor
- Below the melodic timeline, show the drum grid (16th note resolution)
- Click cells to toggle kick/snare/hi-hat hits
- Drag to set velocity (drag up = louder)
- BPM display with manual override input

### Save Corrections
- "Save Corrections" button: writes all manual changes to `manual_corrections` table in Supabase and sets `verified = true` on the transcription row
- Changes are merged into the result_json on read (corrections override original notes by index)
- "Reset to AI output" button: clears all manual corrections for this segment

## UI / DESIGN REQUIREMENTS

**Theme:** Dark industrial — deep black backgrounds, copper/brass accent color (#b5651d or similar warm brass), cream/ivory text. Reflects the brass instrument aesthetic of the band.

**Typography:** 
- Use a clean, slightly condensed sans-serif for headings (Barlow Condensed or similar from Google Fonts)
- Use a monospace font for all sargam notation output (JetBrains Mono or IBM Plex Mono)
- Regular body text: a neutral readable sans-serif

**Note Chips (sargam syllables):**
- Rounded pill shape
- Shuddha notes: solid fill with brass accent color
- Komal notes: outlined/ghost variant with underline
- Tivra Ma+: distinct gold/highlighted chip
- Upper octave (with `'`): slightly brighter background
- Lower octave (with `,`): slightly dimmer background

**Loading States:**

The transcription flow has two distinct wait phases that must be communicated separately:

**Phase 1 — Service Wake-Up (cold start):**
Before submitting the audio file, the Next.js API route pings the Python service `/health` endpoint first. While this ping is in flight, show:
